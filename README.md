### СЦЕНЫ
Вся логика разработчика пишется в сценах. Физика, объекты, управление всё пишется в сценах. Сцена это класс который наследуется от общего класса Scene и живёт как обычный объект, не смотря на то что все модули это статичные классы

## ИНТЕРФЕЙС ПРИКЛАДНОГО ПРОГРАММИРОВАНИЯ
Здесь я поясняю за то, как разработчику сделать игру на моём движке.

### ОСНОВА
Вся логика пишется в сценах. Движок даёт лишь управление, а физику и математику определяет разработчик.

Структура сцены выглядит так:
```cpp
#ifndef NAMESCENE
#define NAMESCENE

class Scene;

class NAMEScene : public Scene {
    // данные конкретно этого класса

    public:
    NAMEScene();

    int  Initialize() override;
    void Update()     override;
    // обязательные функции
};

#endif
```

**Куда это прописывать:**
1. Этот код пишется в файл `include\scenes\NAMEScene.hpp`.
2. Обязательно нужно добавить `#include <scenes/NAMEScene.hpp>` в файл `include\scenes\list.hpp`.
3. Вся логика пишется в `src\scenes\NAMEScene.cpp`.
4. Так же надо открыть `src\game.cpp` и переписать строчку `currentScene = new ` указав первую сцену которая появится в игре.

> ⚠️ **Важно:** Движок не умеет автоматически сканировать файлы, поэтому при добавлении каждой новой сцены нужно руками открывать и дописывать её в файл `CMakeLists.txt`.


### ЛОГИКА
Чтобы работать с железом, используется:

#### ИГРА (Game)
Центр, база, фундамент. место где всё рулится. Инициализирует все модули и запускает главный цикл. Имеет единственную нужную для разработчика функцию, и это `Game::SetScene();`, но о ней подробнее в блоке про **Fx**.

<br>


#### РЕНДЕР (Render)
Данный модуль почти не нужен разработчику. Его задача взять реестр текущей сцены и вручную отрисовать всё что там есть. Рендер получает реестр благодаря модулю Game и Fx


<br>


#### ГЕОМЕТРИЯ (Geometry)
Данный модуль для разработчика идентичен с рендером - почти не нужен ему.


<br>


#### РЕЕСТР (registry)
Каждая сцена имеет свою копию **registry** и при удалении сцены удаляются и все объекты. Сам по себе класс не статичный, ибо каким раком тогда каждый класс мог иметь свою копию?
Реестр это:
Статичный массив на N количество объектов (все сцены имеют общий размер реестра) по умолчанию стоит 512
Каждый объект имеет компонент:
Каждый объект имеет компоненты:
* **Position** — координаты объекта в пространстве (`int32_t vx, vy, vz`).
* **Size** — размеры объекта (`uint16_t w, h`).
* **Rotation** — поворот объекта (`int16_t vx, vy, vz`, пока не используется).
* **Color** — цвет объекта (`uint8_t r, g, b`).
* **Mesh** — полигональная сетка объекта (компонент):
```cpp
typedef struct {
    Polygon* triangles;
    uint16_t count_triangles;
} Mesh;
```

Внутренние структуры данных (не являются компонентами объекта):
* **Polygon** — треугольник полигональной сетки, содержащий массив из 3 вершин (каждая вершина: `int16_t vx, vy, vz`).
* **Texture** — текстура (ассет изображения):
```cpp
typedef struct {
    RECT prect;
    RECT crect;

    uint16_t u_offset;
    uint16_t v_offset;
	
    Size size;

    uint8_t tpage_mode;
    uint8_t tim_mode;
} Texture;
```
<br> 

Для создания объекта используется следующий паттерн:
```cpp
int ID = registry.CreateEntity();
registry.positions[ID] = {0, 0, 0};
// ... и остальные компоненты
```
Для удаления объекта используется команда `registry.DestroyEntity(ID);`

А так же каждый объект имеет массив флагов:
```cpp
    ACTIVE    = 1 << 0,        // 1  (00000001) -              Активен
    VISUAL    = 1 << 1,       // 2  (00000010) - Визуализация включена
    PRIMITIVE = 1 << 2,      // 4  (00000100) -     Примитивы включены
    MESH      = 1 << 3,     // 8  (00001000) -        3D режим включен
    COLOR     = 1 << 4,    // 16 (00010000) -             Цвет включен
    TRANS     = 1 << 5,   // 32 (00100000) -     Прозрачность включена

    ABR_0     = 0 << 6,  // (00) - 50% + 50% (Дефолт, стекло/вода)
    ABR_1     = 1 << 6,  // (01) - 100% + 100% (Аддитивный, огонь/свечение)
    ABR_2     = 2 << 6,  // (10) - 100% - 100% (Вычитание, потемнение)
    ABR_3     = 3 << 6   // (11) - 100% + 25% (Слабое, подсветка)
```
при registry.CreateEntity поднимается флаг `ACTIVE`, остальные поднимать нужно вручную с помощью `registry.flags[ID] |= (VISUAL | COLOR | ...);`

#### УПРАВЛЕНИЕ (Pad)
Для этого модуля нужен `#include <pad.hpp>`
Он позволяет узнать нажата ли определённая кнопка на геймпаде с помощью Pad::States & BUTTON (возвращает 1 если кнопка нажата).
Имена не совпадают с названиями кнопок физического геймпада PS1, вместо этого используются следующие абстрактные названия:
```
	PAD_START    = START
	PAD_TRIANGLE = CANCEL
	PAD_LEFT     = LEFT
	PAD_RIGHT    = RIGHT
	PAD_UP       = UP
	PAD_DOWN     = DOWN
	PAD_CROSS    = USE
	PAD_CIRCLE   = ACTION
	PAD_L1       = INFO
	PAD_L2       = ITEMS
	PAD_R1       = MODIFIER
	PAD_R2       = UTILITY
```
Сделано это для того, чтобы в будущем можно было динамически менять настройки управления нативно.
Менять управление во время игры или проверять напрямую сами кнопки пока что нельзя.
Вы всё ещё можете открыть `src\pad.cpp` и дать другие названия которые перечислены в `include\pad.hpp` (спойлер - их всего 12, как и кнопок геймпада, потому для новых названий придётся дописать список).

#### ДИСК И ПАМЯТЬ (Parser)
Это мульти инструмент для:
1. Чтения с диска.
2. Запуска cd-da музыки.
3. чтения и записи карт памяти.

Но он не парсит файлы. Он не понимает что такое .tim, .vag или .mdl, в основном потому что модули для которых нужны файлы сами понимают как эти самые файлы читать.

**Для чтения с диска:**
* `Parser::ReadFile(name)` Начать чтение файла. Имя пишется **капсом** в виде текста "FOLDER\FILE.TXT" до **16** символов (дописывать в конце ";1" не нужно).
  
* `status = Parser::CheckRead(mode)` Проверка чтения файла. mode=0 останавливает код до тех пор, пока лазер не закончит чтение файла. mode=1 лишь один раз смотрит, видит что закончено и возвращает 0 или -1 если не закончено. Так же функция может вернуть -2 если в чтении файла была ошибка.
  
* `uint32_t* buffer = Parser::LoadFile()` возвращает указателем весь файл. Отсутствует защита - если не копировать данные, буфер будет перезаписан чтением нового файла.
  
* `size = Parser::GetSizeFile()` возвращает число размера в байтах.

**Для запуска музыки с диска:**
* `Parser::Play(n)` Сразу включает музыку. n это число номер трека (по стандарту треков playstation первый трек это сам код в формате iso9660, потому в большинстве случаев счёт идёт с 2 до 99).
  
* `Parser::SetVolume(L, R)` Устанавливает громкость. Эта громкость работает для любого трека и не стирается при новом треке. минимальное значение 0 (0x00) максимальное значение 16386 (0x3fff), есть встроенная защита от переполнения громкости (защита в большей части аппаратная).
  
* `Parser::Pause()` Ставит трек на паузу.
  
* `Parser::Resume()` Продолжает воспроизведение трека с момента где был остановлен
  
* `Parser::Stop()` Полностью останавливает диск. Замедляет чтение с диска на пару секунд (железо раскручивает физический диск).
  
* `Parser::IsPlaying()` Возвращает 1 если трек всё ещё играет и 0 если трек закончился. Нужна для циклической игры или других идей которые придумают разработчики.

**Для записи и чтения карт памяти**
> НЕ РАБОТАЕТ. Причина: трудность найти документацию библиотеки на которой был основан движок и отличие от реализации в оригинального PSY-Q

#### ХРАНИЛИЩЕ (Storage)
Данный модуль нужен вкратце для того, чтобы передавать данные между сценами, ведь при смене сцен старая удаляется полностью.
1. Данные в виде файлов.
2. Есть буфер для малых данных (например чисел или конфигов).
3. Есть буфер Scratchpad.

По стандарту модуль может держать до 64 файлов.

**Для создания файла:**

* `id = Storage::AddFile(size, buffer)` Создаёт файл. size указывается в байтах, а buffer в виде указателя. Сомнительная деталь - пред этим идёт поиск таких же файлов, чтобы не записывать дважды одну и ту же текстуру или звук, тем самым могут быть проблемами для других данных, например конфигов которые должны меняться.
  
* `File file = Storage::GetFile(id)` Возвращает файл.
* `File` состоит из:
  * `.data` - указатель на данные
  * `.size` - возвращает размер в байтах (с округлением до степени 4)
  
* Storage::RemoveFile(id) Освобождает память файла.

**Для записи в буфер:**
> Никак, пока не реализовано. Причина - автор не решился как реализовать чтобы было красиво и удобно.
> Можно просто открыть `include\storage.hpp`, перенести строку буфера в область public и использовать зная заранее какие ячейки занимает какие данные

**Для работы с Scratchpad:**
Обновление - просто `Storage::scratchpad[0-255]` и всё. Память быстрая, соответственно платит разработчик запоминанием какие индексы и тд.

#### ЗВУК (Sound)
Модуль для звуков. Буквально в день написания этой документации я переписал почти с нуля этот модуль.
1. Модуль сам может хранить N количество звуков, по стандарту 256. Тем самым проблем с парсером быть не должно.
2. Имеет карту приоритетов, тем самым большое количество птиц не помешают воспроизвестись реплике персонажа или другому важному звуку.
3. Полный (вроде бы) доступ к всем возможностям чипа SPU.

**Загрузка данных:**
* `id = Sound::Load(name)` Загружает аудиофайл с диска в память «встык» и возвращает его уникальный ID. Нужен для простоты и удобства.
* `id = Sound::SetAudio(data)` Регистрирует звук напрямую из сырого буфера в памяти. Нужен для оптимизации когда во время чтения файла сцена инициализирует другие данные.

**Настройка эффекта:**
* `Sound::SetVolume(id, L, R)` Устанавливает громкость звука отдельно для левого и правого каналов. Максимальное значение `0x3fff`, имеется защита от переполнения банальным удалением двух старших бит, то есть 16384 для spu станет 0
* `Sound::SetPitch(id, pitch)` Меняет частоту дискретизации звука относительно текущей частоты. То есть не абсолютное значение, а допустим 50 или -50 это выше и ниже относительно исходного файла соответственно.
* `Sound::SetADSR(id, a, d, s, r)` Настраивает аппаратную огибающую звука PS1. За атаку, спад, сустейн и релиз читайте документацию плойки, я не музыкант и в душе не чаю что делают каждый кроме r (вроде бы делает плавное затухание).
* `Sound::SetPriority(id, priority)` Задает приоритет звука. По умолчанию у всех приоритет 0. Если все каналы заняты, то модуль перед тем, как выкинуть новый звук, ищет канал с самым низким приоритетом для замены того звука на новый звук. 

**Воспроизведение:**
* `Sound::Play(id)` Простое воспроизведение звука. Движок сам найдет свободный канал.
* `Sound::PlayEx(id, channel, L, R)` Возможно удалю, реализации ещё нет ибо лень. Аналог команды Play с ручным указанием канала.

#### АНИМАЦИИ ПЕРЕХОДА (Fx)
Важное уточнение - Имя **Fx** было выбрано связи с тем, что *SceneTransition* выглядит глупо для человека не знающего английского, то есть для меня. Эффектов в модуле почти нет и нужен он только для анимации переходов между сценами.
1. Для использования **Fx** нужен `Game`, а точнее `Game::SetScene(scene, in, out)`.
2. Модуль задуман как изменяемый разработчиками, ведь разным играм нужны разные анимации, а запихнуть все анимации которые возможны не хватит оперативной памяти консоли.
3. По умолчанию есть анимация фейда, свайпа (не рабочий и пустой), а так же шахматки и плавающей шахматки.
4. Первая сцена появляется сразу. Для анимации первой сцены лучше создать нулевую сцену типа LoadingScene и в ней вызвать нужную вам первую сцену.

при вызове `Game::SetScene()` происходит перехват главного цикла самим модулем **Fx**, сцена продолжает n количество кадров работать пока экран не будет закрыт полностью, после удаляется из памяти, инициализируется новая сцена и **Fx** проигрывает n количество кадров сцены пока анимация не закончится, после чего управление обратно переходит модулю Game.

* `game::SetScene(new Scene(), in, out)` Запускает анимацию. Задумана как защищённая, то есть писать if (playing_fx) не нужно. in это анимация которая закрывает экран от старой анимации, а out это анимация которая уходит показывая новую сцену.
> ⚠️ Есть небольшие баги при попытке сцены вызвать свою копию (например в TestScene вызов `game::SetScene(new TestScene(), 3, 2);` во время out сцена как будто не изменилась, а после окончания работы Fx всё резко возвращается на то, как изначально выглядела сцена).
> Баг исправляться вряд-ли будет, ведь логически причины появления этого бага нет, порядок инициализации, удалении старой сцены и всë остальное написано правильно. Тут либо я слепой, либо виноват компилятор, либо я вообще хз.
  
* `Fx::SetFrame(count)` Определяет количество кадров анимации. Так как в базовых анимации лежит не фиксированное `+5` анимация будет медленнее если указать больше фреймов. количество отвечает за длительность всей анимации без учёта инициализации новой сцены, то есть при count=500 анимация с старой сцены в условный чёрный экран будет 250 кадров и так же 250 кадров при анимации с чёрного экрана в новую сцену.

1. Это прототип движка, не релиз.
2. Я целюсь на крупный функционал типа полного доступа к функционалу чипа spu или всех 4 вариантов abr прозрачности.
3. Мне лень такую мелочь исправлять, по крайней мере сейчас.

Чуть не забыл - для загрузки файлов и треков читайте `iso.xml` - там Lameguy64 всё расписал на английском + есть базовые текстуры и треки которые оставил я для демо сцен.
